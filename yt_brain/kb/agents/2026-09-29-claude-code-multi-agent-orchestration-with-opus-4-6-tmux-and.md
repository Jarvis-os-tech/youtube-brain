## Core Concept

The video argues that Claude Code's experimental agent-teams feature — running Claude Opus 4.6 inside tmux panes, backed by E2B agent sandboxes and a multi-agent observability UI — lets you "scale our compute to scale our impact," and that the real bottleneck in agentic engineering is no longer the models but the engineer's ability to prompt-engineer and context-engineer teams of agents toward one goal. Three capabilities are combined: multi-agent orchestration (create a team, spawn tasks that become agents, run in parallel, shut down, delete the team), multi-agent observability (trace every tool call and event), and agent sandboxes (isolated execution so work happens off-device). The closing argument is that models and tools will keep changing, so the constant constraint is the engineer's own knowledge of the available tool surface — hence the "core four — context, model, prompt, tools" framing and the emphasis on digging into each release.

## Technical Details

- **Models**: Claude Opus 4.6 as primary/orchestrator; Haiku used for some sub-agents. The prior generation is referred to only via a garbled phrase ("As of Sonic 4.5" / "Sonnet 4.5") in the transcript.
- **Feature flag**: experimental agent teams in Claude Code, set via environment variable before launch.

```bash
which claude
export CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1
tmux
claude
ls
```

- **Multi-agent orchestration architecture**:
  - Primary/orchestrator agent → creates task list (centralized hub) → creates team → assigns one task per member.
  - Tasks spawn agents; agents run in parallel in their own tmux panes; each has its own context window, model, session ID, and name.
  - Shutdown → tasks deleted → panes removed → team deleted → context reset for the next team.
- **Tool categories (three)**:
  - Team management — `team_create`, `team_delete`
  - Task management — `task_create`, `task_list`, `task_get`, `task_update`
  - Communications — `send_message`
- **Orchestration lifecycle**:
  1. Create the team
  2. Create the tasks
  3. Spawn the agents
  4. Work in parallel
  5. Shut them all down
  6. Delete the team
- **Execution environment**: E2B agent sandboxes for isolated work; E2B key validation happens on agent-sandbox skill invocation. The agent sandbox lives outside the sandbox and talks to E2B.
- **Observability**: a separate UI captures session start/end, user-prompt-submit, and per-agent tool-call streams in "swim lanes" you can click into — the point is to "jump in here and we can investigate and see the communication, see the tasks between our agents that we kicked off. We see all the events."
- **tmux as the visualization layer**: one pane per sub-agent, giving a real-time layout of team membership plus per-pane status lines and context meters. tmux changes control bindings (`Ctrl+B` prefix, then `[` / `Esc` for copy mode).
- **Skills used**: an "agent sandbox" skill (backslash command) invoked as instructions, plus a "backslash command" skill for `\reboot`.
- **Prompt engineering pattern**: information-dense trigger keywords (`build a new agent team`) → tool routing (`using agent sandboxes`) → explicit skill invocation (`\reboot`) → explicit scope and completion requirements (`mount one through four`, `be sure to set up every agent`, `spin up a new agent team to do this work for you`).
- **Run modes demonstrated**: tmux (multi-pane orchestration) vs. a flat single Claude Code instance (no tmux needed for simple sandbox listing/spawning).
- **Trade-offs**:
  - tmux adds control-binding friction and pane-management overhead but is the only way to get the visual team view.
  - API billing is required once plan limits are hit.
  - Sandboxes are ephemeral (~12 h), so state must be copied out.
  - Spawning many parallel agents burns credits fast.
  - Deleting teams forces context-engineering discipline — reset rather than letting one context grow unbounded.
  - Tooling churn is treated as a given, not a fixed target; the engineer's familiarity is the limiting factor.
